## What the service exports

`GET /metrics` (Prometheus text format, **no authentication**: keep it on a private network or
behind the reverse proxy's allow-list). Names from `service/crates/face-server/src/metrics.rs`:

| Metric | Type | Labels |
|---|---|---|
| `face_requests_total` | counter | `endpoint`, `status` (HTTP code) |
| `face_request_duration_seconds` | histogram (5 ms ... 30 s) | `endpoint` |
| `face_stage_duration_seconds` | histogram | `stage`: queue, upload, decode, detect, landmarks, segment, measure, document, risk, embed, evaluate, output |
| `face_check_status_total` | counter | `check`, `status` (pass, fail, undetermined, skipped) |
| `face_verification_outcome_total` | counter | `outcome` (verified, rejected, review, retake) |
| `face_inflight` | gauge | requests holding a processing slot |
| `face_queue_depth` | gauge | requests waiting for a slot |
| `face_unread_body_total` | counter | `outcome`: bodies left unread by an early response (401, 413, 429, 503...): `drained`, `not_sent` (Expect: 100-continue), or closed unread: `too_large`, `busy`, `timeout`, `error` |
| `face_rate_limited_total` | counter | `project`, `reason` (`rate`, `concurrency`): `429 rate-limited` answers (P4) |
| `face_config_reloads_total` | counter | `result` (`ok`, `error`): hot reloads of keys and profiles (P4) |

Not exported (the dashboard and alerts work around them):

- **Problem codes.** Only the HTTP status is a label. The dashboard maps status to the problem
  code(s) of `contracts/openapi.yaml` (429 = rate-limited); 503 (overloaded / not-ready) and 422
  (image-decode-failed / image-too-large) stay ambiguous. The exact code is in the JSON log line of each request.
- **Readiness.** `/health/ready` is not a metric. Probe it with the blackbox exporter (below).
- **Process CPU and memory.** No `process_*` metrics (the `prometheus` crate is built without its
  `process` feature). Use windows_exporter's process collector on Windows or cAdvisor in a
  container; the dashboard's Process row reads either.
- **Limits.** `max_concurrency` and `queue_limit` are not exported; the queue alert hard-codes 80%
  of the default `queue_limit` (32).
- **Subject of a check.** `face_check_status_total` does not say whether a result came from a
  selfie, a document, or a verification's probe or reference.

## Scrape configuration

```yaml
# prometheus.yml
rule_files:
  - /etc/prometheus/veriface/alerts.yml

scrape_configs:
  - job_name: veriface            # alerts.yml expects this job name
    scrape_interval: 15s
    static_configs:
      - targets: ["face-host-1:8080", "face-host-2:8080"]

  # Readiness: blackbox exporter, http_2xx module, against /health/ready.
  - job_name: veriface-ready      # alerts.yml and the dashboard expect this job name
    metrics_path: /probe
    params: { module: [http_2xx] }
    static_configs:
      - targets: ["http://face-host-1:8080/health/ready", "http://face-host-2:8080/health/ready"]
    relabel_configs:
      - { source_labels: [__address__], target_label: __param_target }
      - { source_labels: [__param_target], target_label: instance }
      - { target_label: __address__, replacement: "blackbox-exporter:9115" }
```

If the configuration sets `health_requires_key = true`, the probe must send `X-API-Key` (blackbox
`http.headers`); prefer a dedicated key with no profiles you care about.

On Windows, windows_exporter with `--collectors.enabled "cpu,memory,process"` and
`--collector.process.include "veriface"` provides `windows_process_*` for the Process row.

## Import the dashboard

- **UI:** Dashboards → New → Import → upload `grafana/veriface.json` → pick the Prometheus data
  source.
- **Provisioning:** copy the file into a folder served by a dashboard provider
  (`/etc/grafana/provisioning/dashboards/*.yaml` with `options.path` pointing at it). The
  `datasource` variable selects the Prometheus source at view time.

Variables: data source, `job`, `instance`, `endpoint` (All = `/v1/*`), `stage`, `check`, and
`probe_job` (the blackbox job name, default `veriface-ready`). Requires Grafana 10 or later.

To change the dashboard, edit `grafana/build-dashboard.mjs` and run
`node ops/grafana/build-dashboard.mjs`; do not hand-edit the JSON. Check the queries against a
Prometheus server that scrapes a running service:

```bash
node ops/grafana/check-queries.mjs http://127.0.0.1:9090
```

## Alerts

`prometheus/alerts.yml` (33 rules):

| Alert | Fires when |
|---|---|
| `VerifaceDown` / `VerifaceAbsent` | scrape fails 2 min / no target 10 min |
| `VerifaceNotReady` | blackbox probe of `/health/ready` fails 3 min |
| `Veriface503WithoutLoad` | 503s with an empty queue and nothing in flight (not-ready, without a probe) |
| `VerifaceInternalErrors` / `...High` | 5xx other than 503 above 1% (10 min) / 5% (5 min) |
| `VerifaceOverloaded` / `...High` | 503 above 5% (10 min) / 20% (5 min) |
| `VerifaceAuthFailures` | 401 above 0.2/s for 10 min |
| `VerifaceUnreadBodiesDropped` | early responses closed with the body undrained (`busy` or `timeout`) above 0 for 10 min |
| `VerifaceRateLimited` | a project gets 429 above 0.1/s for 15 min (info) |
| `VerifaceConfigReloadFailed` | any failed hot reload in the last 10 min |
| `VerifaceLatencyBudgetBurnFast` / `...Slow` | SLO "99% of `/v1` requests within 5 s": burn rate 14.4 (1 h and 5 min) / 6 (6 h and 30 min) |
| `VerifaceRequestTimeouts` | requests above the 30 s bucket |
| `VerifaceQueueSaturated` / `VerifaceQueueing` | queue averaged >= 26 (80% of 32) for 5 min / >= 1 for 15 min |
| `VerifaceCheckRejectRateRising` | a check's hourly reject ratio is > 2x and > 10 points above its 7-day average (min. 36 evaluations/h) |
| `VerifaceCheckRejectRateCollapsed` | a check that rejects > 5% on average drops below a third of that |
| `VerifaceCheckUndeterminedRising` | as above, for undetermined results |
| `VerifaceVerificationOutcomeShift` | an outcome's hourly share moves > 15 points from its 7-day average |

The drift rules need 7 days of history before they mean anything. Tune the SLO threshold, burn
rates and drift margins to the deployment's traffic.

Test the rules (promtool ships with Prometheus):

```bash
promtool check rules ops/prometheus/alerts.yml
promtool test rules ops/prometheus/alerts.test.yml ops/prometheus/alerts-drift.test.yml
```

## Load and soak tests

```bash
# Key from tools/console/.env.local (VERIFACE_API_KEY), never printed.
node ops/loadtest/loadtest.mjs --url http://127.0.0.1:18100 --env-file tools/console/.env.local \
  --profile fixtures --concurrency 4 --duration 120 --json result.json

# Soak: memory sampled every 30 s, growth after warm-up > 10% flagged (exit code 1).
node ops/loadtest/loadtest.mjs --url http://127.0.0.1:18100 --env-file tools/console/.env.local \
  --profile fixtures --concurrency 4 --duration 1800 --soak --warmup 300
```

The default mix is 2 quality : 1 document : 1 verification (half of the verifications pair a
document with the same person's selfie). Run against your own instance, never against a shared
one. `node ops/loadtest/loadtest.mjs --help` lists every option.
